# 動画のあとに読むGitとGitHub

[Gitのアニメーション](what-is-git-branch-150sec.html)を見たあと、操作中に分からなくなったところを確かめるページです。
動画で見たブランチとローカル・リモートの関係を、この勉強会の`index.html`に当てはめて説明します。
実際に入力するコマンドは[README](../README.md#1-リポジトリを手元に用意する)にあります。

## Gitは何のために使うのか

ページを直すたびに`index-final.html`、`index-final2.html`とファイルを増やすと、どれが最新版か分かりにくくなります。
Gitなら同じ`index.html`を編集しながら、必要な時点の変更をコミットとして記録できます。
後から「いつ、何を変えたか」も調べられます。

Gitは手元のパソコンでも動く、変更履歴を管理する道具です。
GitHubは履歴を共有し、PRやCIを使うサービスです。
GitHubの画面を開かなくてもコミットできますが、そのコミットをほかの人に見せるにはpushが必要です。

## 全体の流れ

![手元のファイルをコミットし、自分のブランチへpushして、mainに向けたPRを作る流れ](images/git-local-remote.png)

図の左は自分のパソコン（ローカル）、右はGitHub（リモート）です。
今回の作業で変更が移る順番を見てみましょう。

| 場所 | 何があるか | 対応する操作 |
| --- | --- | --- |
| 作業中のファイル | エディタで保存した`index.html` | 編集、`git diff`で確認 |
| ステージ | 次のコミットに入れると選んだ変更 | `git add`、`git diff --staged`で確認 |
| 手元のリポジトリ | コミットとして記録した履歴 | `git commit`、`git log`で確認 |
| GitHub上の自分のブランチ | push済みのコミット | `git push` |
| GitHub上の`main` | 共有する基準の履歴 | PRで取り込みを提案 |

リポジトリは、ファイルと変更履歴をまとめて管理する場所です。
`git clone`でGitHub上のリポジトリをコピーすると、手元にもリポジトリができます。
コピー元には`origin`という名前が付きます。
今回は用意されたリポジトリをコピーするので、`git init`や`git remote add`は実行しません。

手元でファイルを保存しても、GitHub上のファイルは変わりません。
コミットした後も、履歴はまだ手元だけにあります。
pushして初めて、GitHub上の自分のブランチにコミットが届きます。

## ブランチは何を分けるのか

動画ではブランチを「コミットに貼る付箋」として描いています。
ブランチは履歴のある時点を指す名前で、コミットが増えると指す先も進みます。
別のフォルダを毎回作る機能ではありません。

今回の`git switch -c workshop/hanako`は、`main`から自分用のブランチを作って切り替える操作です。
`-c`を付けない`git switch workshop/hanako`は、すでにあるブランチへ切り替えます。

全員が同じ`index.html`を編集しても、自分のブランチにコミットする間は共有用の`main`に変更は入りません。
`git branch --show-current`で、今いるブランチを確かめられます。

`git push -u origin workshop/hanako`で初めて、GitHub側にも同じ名前のブランチが作られます。
名前が同じでも、手元とGitHub上では別々のブランチです。
新しいコミットを作ったら、もう一度pushします。

`main`も手元とGitHubにそれぞれあります。
ほかの人がGitHub上の`main`を更新しても、手元の`main`は自動では更新されません。
今回の必須課題ではclone直後に自分のブランチを作るので、`main`を更新する操作は不要です。

## `git status`の2文字を読む

動画では、ファイルを編集してからコミットするまでの操作を省略しています。
実際には`git add`で次のコミットに入れる変更をステージに選びます。
`git status --short`で、その前後の状態を確かめましょう。
ファイル名の前の2文字は、左がステージ、右が作業中のファイルの状態です。

| 表示例 | 今の状態 |
| --- | --- |
| ` M index.html` | ファイルを編集したが、まだステージに載せていない |
| `M  index.html` | 変更をステージに載せた |
| `?? practice-note.txt` | Gitがまだ追跡していない新しいファイル |
| 何も表示されない | 未記録の変更がない |

`git add index.html`は、現在の`index.html`を次のコミットに入れる候補としてステージに載せます。
別のメモも編集しているときに`git add .`を使うと、そのメモまで載ってしまいます。
この課題では`index.html`だけを指定してください。

ステージに載せる前の差分は`git diff -- index.html`、載せた後の差分は`git diff --staged -- index.html`で見ます。
差分の`-`は変更前、`+`は変更後の行です。
`git diff`が空になっても、ステージに載せた内容は残っています。

`git commit`でステージの内容を手元の履歴に記録します。
コミットには識別用のIDと、自分で書いたメッセージが付きます。
後から見返すときは`git log --oneline`で履歴を短く表示できます。

## PRと`git pull`は別の操作

pushした後、GitHubでPRを作ります。
PRは「自分のブランチの変更を`main`へ取り込んでください」という提案です。
「Files changed」には、提案した変更が表示されます。

今回の完了条件は、PRを作ってCIが成功することです。
CIは、提出したファイルとPR本文を自動で確認します。
レビュー承認とマージは完了条件に含めません。
PRやCIだけでは`main`は変わらず、マージすると変更が`main`に入ります。

`git pull`は、GitHub上で進んだ履歴を手元に取り込み、今いるブランチに反映するコマンドです。
PRを作る操作ではありません。
動画ではマージ後の`main`を手元に取り込む場面で使っています。
今回の必須手順では`git pull`を実行しません。

動画のマージ場面では、2つのブランチが同じ場所に行を追加しています。
実際のGitでこの例をマージすると、どちらを残すか確認が必要なコンフリクトになります。
今回はマージもコンフリクト解消も扱わず、ブランチが分かれて合流するイメージとして見てください。

PRで修正が必要になったら、同じブランチでファイルを直してコミットし、もう一度pushします。
GitHubは新しいコミットを既存のPRに追加し、CIを再実行します。
PR本文だけならGitHub上で編集できます。
[READMEの修正手順](../README.md#6-ciの結果を確認し必要なら同じprを直す)を見て進めてください。

履歴の調べ方や一時退避も試したい人は、[追加課題](advanced-git.md)に進めます。
